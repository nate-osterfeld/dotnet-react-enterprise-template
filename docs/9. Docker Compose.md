Here is the comprehensive documentation breakdown for your **`docker-compose.yml`** file, explaining its purpose, its mechanics, how it handles local persistence, and how it bridges your work into cloud environments like Azure.

> Note: We will not be using docker-compose as it is unnecessary for our purposes. This means, however, that our local persistence (mssqllocaldb) will not be accessible from inside the container. Once it is hosted to the cloud this will change as the environment variables will be injected into the app and accessible on a public network. If we added docker-compose we could create an instance of SQL Server inside its own container with a local network to bridge them, but again this is not necessary for our app to run.
### 1. The Local `docker-compose.yml` File with Detailed Comments

Create a file named **`docker-compose.yml`** in your root workspace (`CapstoneApp`) and paste the following content:


```bash
version: '3.8'

services:
  # ==========================================
  # DATABASE SERVICE: SQL Server for Linux
  # ==========================================
  # Spins up an official Microsoft SQL Server container to provide a persistent database engine locally.
  sqlserver:
    image: mcr.microsoft.com/mssql/server:2022-latest
    container_name: capstone_sql
    environment:
      - ACCEPT_EULA=Y
      - SA_PASSWORD=YourStrong@Password123  # Required default system administrator password
    ports:
      - "1433:1433"  # Maps local machine port 1433 to the container's SQL Server port
    volumes:
      - sqldata:/var/opt/mssql  # Persists database files on a Docker volume so data survives container restarts

  # ==========================================
  # APPLICATION SERVICE: Your Monolith App
  # ==========================================
  # Builds and runs your full-stack .NET and React monolith container using your root Dockerfile.
  app:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: capstone_app
    ports:
      - "8080:8080"  # Maps your local port 8080 to the container's web server port
    environment:
      - ASPNETCORE_ENVIRONMENT=Development
      # Injects a connection string targeting the 'sqlserver' container service defined above
      - ConnectionStrings__DefaultConnection=Server=sqlserver;Database=CapstoneDb;User=sa;Password=YourStrong@Password123;TrustServerCertificate=True;
    depends_on:
      - sqlserver  # Ensures the database container starts up completely before launching the web app container

# ==========================================
# VOLUMES: Persistent Storage Definition
# ==========================================
volumes:
  sqldata:
```

### 2. Intended Purpose and Core Mechanics

- **Intended Purpose:** While your multi-stage `Dockerfile` packages your application code into an image, **`docker-compose` is your local orchestration tool**. It allows you to spin up multiple interdependent containers (your application server and your SQL Server database) simultaneously with a single terminal command (`docker compose up --build`).
    
- **The Two Core Services Explained:**  
    1. **The Database Service (`sqlserver`):** Pulls the official Microsoft SQL Server image, initializes an instance, and maps a dedicated Docker volume (`sqldata`). This volume ensures that your database tables and rows aren't wiped out every time you stop or restart your containers.
    2. **The App Service (`app`):** Automatically builds your root `Dockerfile` and links it to the database container. The `depends_on` rule guarantees your app doesn't try to boot up and run Entity Framework migrations before the database engine is ready to accept connections.

### 3. How `docker-compose` Relates to Local Development vs. Cloud Environments

It is vital to understand how local orchestration compares to cloud execution:

- **Local Orchestration (`docker-compose.yml`):** Used strictly on your local machine for rapid containerized testing. It links your app container to a local SQL Server container via internal Docker networking (using `Server=sqlserver`).
- **Solo Offline Coding:** When you want to use **SSMS directly against a local Windows instance** (`(localdb)\mssqllocaldb`), you bypass `docker-compose` entirely and run your app natively in Visual Studio using `appsettings.Development.json`. `docker-compose` is an _alternative_ local environment option if you want everything fully containerized.
- **Cloud Environments (Dev, Test, Prod in Azure):** **You do not use `docker-compose` in Azure.** In the cloud, Azure manages the infrastructure hosting:
    - Your compiled app container runs natively as a managed **Azure Container App**.
    - Your database runs as a fully managed **Azure SQL Database** service.
    - GitHub Actions bridges them by injecting the cloud database connection string directly into your Azure Container App environment variables.

### 4. How This Sets Us Up for CI/CD and Multi-Environments

By mastering both the `Dockerfile` and `docker-compose.yml`, you establish a complete blueprint for professional software delivery:

1. **Local Consistency:** You can spin up the exact same stack locally via containers that will eventually run in the cloud.    
2. **Pipeline Decoupling:** Your GitHub Actions CI/CD workflows will build the application image via the `Dockerfile` and push it to Azure, while environment-specific parameters (like your Dev, Test, or Prod Azure SQL connection strings) are handled safely through cloud secrets without altering a single line of code.
